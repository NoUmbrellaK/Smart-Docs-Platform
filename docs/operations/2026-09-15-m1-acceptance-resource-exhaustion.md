# M1 验收资源耗尽事故记录（2026-09-15）

## 结论

2026-09-14 至 2026-09-15，这台阿里云 ECS 发生了三次非正常重启。根因不是磁盘空间耗尽，也没有发现 OOM Killer、内核 panic 或 EXT4 I/O 错误；直接诱因是 M1 验收期间反复执行全量清理构建、隔离 MySQL 初始化和二十轮真实进程故障恢复，并曾在 2 vCPU 主机上使用 `SMARTDOCS_BUILD_JOBS=16`。CPU、内存页整理和云盘 IOPS 同时进入压力区后，内核线程 `kcompactd0` 长时间处于不可中断的 I/O 等待，实例最终失去响应并被重启。

本事故不要求立即物理扩容。当前开发与单次验收可以通过降低并发、禁止并行验收和减少全量重建安全推进；如果需要频繁或并行执行完整验收，应迁移到独立、经过容量测量的 CI/构建节点，而不是继续给业务主机施压。

## 影响与时间线

- 2026-09-14 18:06 左右，阿里云诊断记录实例 CPU 负载达到 100%。
- 19:02 至 20:16，内核日志反复报告 `kcompactd0` 阻塞 120、241、362、483 秒；调用栈经过 `io_schedule`、`wait_on_page_bit_common`、`__lock_page`、`__unmap_and_move`、`migrate_pages` 和 `compact_zone`。
- 21:13 左右，阿里云诊断记录云盘 I/O 延迟/IOPS 受限；随后日志停止，实例约在 21:15 重新启动。
- 2026-09-14 23:59:10 至 2026-09-15 00:00:00，验收命令以 `SMARTDOCS_BUILD_JOBS=16` 执行；系统日志在 00:00:41 截止，实例约在 00:03:44 重新启动。
- 00:28 至 00:30，再次出现集中构建产物写入；日志在 00:30:54 截止，实例约在 00:35:57 重新启动。
- 三次后续启动均报告文件系统未正常卸载，说明此前不是正常关机流程。

## 环境与排除项

事故时主机为 2 vCPU、约 3.4 GiB 内存、无 swap，根盘 40 GiB。诊断时根盘使用约 63%，inode 使用约 12%，因此容量和 inode 耗尽可以排除。日志检索没有发现以下信号：

- `oom-kill` 或 `Out of memory`；
- kernel panic、soft lockup 或 hard lockup；
- EXT4 I/O error；
- 三次故障前的正常 shutdown/reboot 序列。

测试服务器中的 `_exit(86)` 仅用于终止被故障注入的 `smartdocs_test_server` 子进程，不会直接重启宿主机。宿主机失去响应来自验收负载和资源配置的组合，而不是该退出码本身。

## 已落地的防护

`test/e2e/run_m1.sh` 现在执行以下前置保护：

- 构建默认使用 1 个 job；
- `SMARTDOCS_BUILD_JOBS` 必须是正整数；
- 构建 job 上限为 `min(在线 CPU 数, 2)`，超过上限会在清理构建和 MySQL 初始化前以 `unsafe_build_parallelism` 退出；
- 普通服务器、管理工具和故障注入测试服务器都从同一 checkout 重新构建并记录 SHA-256；
- 普通服务器会先完成一次启动冒烟检查，故障注入只由测试服务器承载；
- checkout 在构建或场景执行期间发生变化时，验收失败，不生成可信的绿色结论。

轻量护栏测试：

```bash
python3 -B test/e2e/m1_harness_self_test.py
bash -n test/e2e/run_m1.sh
```

## 后续操作规范

1. 在本机运行完整 M1 验收时只使用默认值或显式设置 `SMARTDOCS_BUILD_JOBS=1`。
2. 同一时间只能运行一个完整验收；不要把 `run_m1.sh`、隔离 MySQL 套件或全量构建并行启动。
3. 日常修改优先使用增量、聚焦测试；`make clean` 加二十轮真实故障恢复只在最终证据采集时执行一次。
4. 运行完整验收前检查 CPU、可用内存、云盘延迟/IOPS 和现有构建进程；资源已处于压力区时延后执行。
5. 完整验收中出现持续高 I/O 等待、D 状态任务或系统交互明显变慢时，停止验收子进程并保留日志，不要立即重复运行。
6. swap 可作为额外缓冲，但不能替代并发限制和独立构建节点；是否增加 swap 或升级实例，应根据后续单次 `-j1` 验收的峰值监控决定。

资源护栏与验收驱动接线使用不启动真实 MySQL、不编译 C++ 的自测验证。为避免再次冲击当前 ECS，本次修复后没有在该主机重跑完整 M1 二十轮验收。因此，修复前生成的结果不能作为当前提交的最终 M1 阶段门证据；Task 12 仍需在安全环境中完成一次与目标提交绑定的完整验收和人工审阅。
